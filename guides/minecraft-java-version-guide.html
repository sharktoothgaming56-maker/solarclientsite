Which Java Version Does Your Minecraft Need?

Minecraft: Java Edition requires a specific Java release for each game version, and the error messages when you get it wrong are famously unhelpful. This is the full mapping, plus how to read the errors and what to do about mixed setups.

Published September 20, 2026 · Covers Minecraft: Java Edition 1.0–1.21 · ~8 min read

Quick answer

  • 1.20.5 and newer: Java 21
  • 1.18 – 1.20.4: Java 17
  • 1.17 – 1.17.1: Java 16
  • 1.16.5 and older: Java 8
  • You can have several installed at once. The launcher picks; the system default does not have to match.

The version chart

Mojang raises the required Java version when the game starts using language or runtime features from a newer release. The requirement is a floor, not an exact match — but going above it is not always safe, for reasons covered further down.

Minimum Java runtime by Minecraft version. Mojang ships a bundled runtime with the official launcher; third-party launchers including SolarClient manage their own.
Minecraft version Required Java Notes
1.20.5 – 1.21.x Java 21 Current requirement. Java 21 is a long-term support release.
1.18 – 1.20.4 Java 17 Covers a large share of modded play. Also an LTS release.
1.17 – 1.17.1 Java 16 The first version to break from Java 8. Short-lived; Java 17 works for most purposes.
1.12 – 1.16.5 Java 8 Forge packs from this era frequently require Java 8 specifically, not merely a minimum.
1.0 – 1.11.2 Java 8 Technically older releases suffice, but Java 8 is what everything is tested against.

Can you just install the newest Java and use it for everything?

For vanilla, largely yes — newer Java runs older Minecraft in most cases. For modded, no, and this is where people get stuck.

The problem is not Minecraft itself but the mod loaders and the mods. Forge for 1.12.2 and similar versions does not run on modern Java. It relies on internal JDK APIs and reflective access patterns that were progressively restricted from Java 9 onwards and eventually blocked outright. Launching a 1.12.2 Forge pack on Java 17 typically produces a wall of reflection errors before the game window ever appears.

The inverse also happens. Mods compiled against Java 17 features cannot be loaded by a Java 8 runtime, which surfaces as UnsupportedClassVersionError.

The practical conclusion: match the version to the game, keep several installed, and let the launcher choose. This is precisely the problem multi-version launchers exist to solve, and SolarClient downloads the correct Adoptium runtime per version and switches automatically — you do not need any Java installed system-wide at all.

Reading the error messages

Java’s version errors are cryptic in a consistent way, which at least makes them learnable.

UnsupportedClassVersionError

java.lang.UnsupportedClassVersionError: net/minecraft/client/main/Main
has been compiled by a more recent version of the Java Runtime
(class file version 65.0), this version of the Java Runtime only
recognizes class file versions up to 52.0

This means your Java is too old. The class file version numbers map to Java releases directly:

Class file versionJava release
52.0Java 8
55.0Java 11
60.0Java 16
61.0Java 17
65.0Java 21

Subtract 44 from the class file version to get the Java release number. Version 65 means Java 21 is required and something older is running.

Reflection and module access errors

java.lang.reflect.InaccessibleObjectException: Unable to make
field private final java.lang.String java.io.File.path accessible:
module java.base does not "opens java.io" to unnamed module

The mirror image: your Java is too new. The module system introduced in Java 9 blocked the deep reflection that older Forge versions depend on. There is no flag worth adding here — install the correct older Java instead.

A window that never appears

If the launcher reports the game exited with code 1 and no window opened, open the log. The real error is almost always one of the two above, printed before the process terminated.

Which Java build should you install?

“Java 17” names a specification, and several organisations ship builds of it. For Minecraft the differences are small but not zero.

  • Eclipse Temurin (from Adoptium) is the default recommendation. Free, permissively licensed, well tested, and what most launchers — SolarClient included — download automatically.
  • Azul Zulu is a solid alternative with broad platform coverage, including builds for Apple Silicon that predated others.
  • Amazon Corretto is a good build with long support timelines.
  • Oracle JDK works but carries licence terms that have changed repeatedly. There is no technical reason to prefer it here.
  • GraalVM occasionally gets recommended for its compiler. Gains in Minecraft are inconsistent, and mod compatibility is less well tested. Not a default choice.

Always take the 64-bit build. A 32-bit JVM cannot address more than about 4 GB, which rules out any meaningful allocation. Also prefer a JRE or JDK from the list above over the consumer “Java” download aimed at browser plugins, which has been end-of-life for years.

Checking what you have

In a terminal:

java -version

Output resembling openjdk version "21.0.4" means Java 21. Note that this reports the default runtime on your PATH, which is not necessarily what your launcher uses — launchers with managed runtimes deliberately ignore the system installation.

To list everything installed on Windows:

Get-ChildItem "C:\Program Files\Java", "C:\Program Files\Eclipse Adoptium" -ErrorAction SilentlyContinue

In game, F3 shows the running Java version in the right-hand column, which is the authoritative answer for the instance actually in front of you.

You probably do not need to install anything

If your launcher manages runtimes, installing Java system-wide adds a version to maintain and a way to confuse yourself later. SolarClient keeps its runtimes in its own directory, fetches the right one per Minecraft version, and removes ones that are no longer referenced. The only reason to install Java yourself is if you also develop Java software.

Does a newer Java run Minecraft faster?

Modestly, yes — where the game supports it. The JVM has had real improvements across releases: better JIT compilation, cheaper garbage collectors, and reduced startup overhead. Java 17 is meaningfully better than Java 8 at the same workload, and Java 21 brought generational ZGC, which matters for large modded heaps.

But the effect is a refinement, not a transformation. Moving from Java 8 to Java 17 on a 1.12.2 pack — where it works at all — will not produce anything like the improvement of installing a modern rendering mod. Set the Java version correctly because the game requires it, then look for frames elsewhere. The FPS guide covers where they actually are.

Running several versions side by side

Nothing prevents multiple Java installations coexisting. Java does not use a single global registration the way some runtimes do — each installation is a self-contained directory, and whichever one launches a program is the one that runs it.

What matters is that each application points at the right one:

  • Managed launchers store a per-instance Java path and use it regardless of system state. Nothing to configure.
  • The system PATH determines what java means in a terminal, and what applications that do not specify a runtime will get. Point this at the newest LTS release you use.
  • JAVA_HOME is used by build tools, not usually by games. Setting it does not change what a launcher does.

If you keep a 1.12.2 pack and a 1.21 world, you need Java 8 and Java 21 on the machine simultaneously. That is normal and supported.
