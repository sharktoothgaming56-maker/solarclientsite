How to Increase Minecraft FPS: A Complete Guide

Minecraft’s frame rate is limited by very specific things — draw call overhead, single-threaded chunk meshing, and garbage collection — not by how many settings you turn down. This guide explains what actually costs you frames, in the order worth fixing.

Published September 20, 2026 · Applies to Minecraft: Java Edition 1.16–1.21 · ~12 min read

The short version

  • Install Sodium first. Nothing else on this list comes close. It replaces Minecraft’s rendering engine and routinely doubles frame rates on its own.
  • Check which GPU is actually running the game. On laptops, Minecraft very often runs on the integrated GPU by default. Fixing that is a one-minute change with a huge payoff.
  • Allocate less RAM, not more. Oversized heaps make stutter worse, not better. 4–6 GB covers almost everything.
  • Render distance is the most expensive single setting, and it scales roughly with the square of the value.
  • Low FPS and “server lag” are different problems with different fixes. Diagnose which one you have before changing anything.

Why vanilla Minecraft runs badly on fast hardware

It is genuinely strange the first time you notice it: a machine that plays modern AAA titles at 120 FPS struggles to hold 60 in a game made of cubes. That is not your hardware being wasted — it is an artefact of how Minecraft was built.

Minecraft: Java Edition grew out of a codebase written in 2009, before the rendering techniques that modern games rely on were standard. Three consequences follow from that, and between them they explain most of the frame rate problem:

  • Draw call overhead. Vanilla issues a very large number of small, separate drawing commands to the GPU rather than batching geometry into a few large ones. Each command has fixed CPU cost. The result is that your CPU spends its time talking to the GPU instead of the GPU spending its time drawing, and your graphics card sits mostly idle.
  • Single-threaded chunk work. When terrain changes or new chunks come into view, the game has to rebuild the mesh for that chunk — work the vanilla engine does largely on the main thread. Your other CPU cores are unused while the frame you are waiting for is blocked.
  • Java memory churn. The game allocates and discards a very large number of short-lived objects every tick. Java cleans those up with a garbage collector, and collection means pausing. Small pauses are invisible; large ones are the stutter you feel.

Every meaningful FPS fix targets one of those three. That is why the order in this guide matters: replacing the renderer addresses the first two directly, and most of the settings people reach for first barely touch any of them.

Is it FPS, or is it the server?

Before changing anything, work out which problem you have, because the fixes do not overlap at all.

Low FPS means the game is drawing few frames per second. The world keeps behaving correctly; it just looks choppy. Moving the mouse feels sluggish. Press F3 and read the number in the top-left.

Server lag — low TPS, or ticks per second — means the world simulation is behind. Blocks take a moment to break, mobs rubber-band, items hang in the air, doors open late. Crucially, your FPS can be a perfectly healthy 200 while this is happening. Minecraft targets 20 TPS; anything below roughly 18 is noticeable.

If you are on a multiplayer server and everyone is experiencing the same delay, it is a server problem and nothing you change locally will help. If it happens in singleplayer, your own machine is running the server, so heavy redstone, large mob farms, or chunk loading can still cause it — and the fix is reducing simulation load, not graphics settings.

Worth installing

The spark profiler is the standard tool for telling these apart properly. Running /spark profiler start, playing for a minute, then /spark profiler stop gives you a shareable report showing exactly which code is consuming your tick time or frame time. It is free, open source, and available for both client and server.

Step 1: Make sure the right GPU is running the game

This is first because it is the single most common cause of “my expensive laptop runs Minecraft at 30 FPS,” it takes about a minute to check, and the improvement can be several hundred percent.

Laptops with both integrated graphics and a dedicated GPU decide per-application which one to use. Windows makes that decision based on heuristics that frequently get Java applications wrong, because the process it sees is javaw.exe, not something it recognises as a game.

To check: press F3 in game and look at the right-hand column. It names the graphics adapter in use. If it says Intel UHD, Intel Iris, or AMD Radeon Graphics on a machine that also has an NVIDIA or dedicated AMD card, you have found your problem.

To fix it on Windows 10 or 11:

  1. Open Settings → System → Display → Graphics.
  2. Choose Desktop app, then Browse.
  3. Point it at the Java executable your launcher actually uses. SolarClient manages its own Java runtimes, so this is inside the SolarClient directory rather than in Program Files — the launcher shows the exact path under Settings → Java.
  4. Select the added entry, click Options, and set it to High performance.
  5. Restart the game and confirm with F3 that the adapter changed.

NVIDIA users can do the same through the NVIDIA Control Panel under Manage 3D Settings → Program Settings, and AMD users through Adrenalin’s per-application graphics profiles. Setting it in Windows is usually enough on modern drivers.

Step 2: Install a modern rendering engine

If you only do one thing from this guide, do this one.

Sodium replaces Minecraft’s chunk rendering pipeline with one written against modern OpenGL. Instead of thousands of small draw calls, it packs chunk geometry into large shared vertex buffers and submits them in batches. It also culls geometry the vanilla engine draws and throws away, and it moves chunk meshing off the render thread.

The practical effect is that your GPU finally becomes the thing doing the work. Improvements vary enormously with hardware — the bigger the gap between your CPU and GPU, the bigger the gain — but doubling frame rate is an ordinary result rather than a remarkable one, and on CPU-limited systems it can be more.

Sodium is Fabric-native and has official NeoForge support in recent versions. On older Forge versions, Embeddium is the maintained port.

Three companions are worth adding at the same time:

  • Lithium optimises the game logic and tick loop — pathfinding, block ticking, collision, chunk management. It changes no game behaviour and is safe on servers. This helps TPS, which Sodium does not touch.
  • FerriteCore reduces the memory footprint of block states, models, and multipart predicates. Less memory in use means less garbage collection pressure, which means fewer pauses.
  • ImmediatelyFast batches the immediate-mode rendering Minecraft still uses for text, items, GUI elements, and particles. Its effect is largest in inventory-heavy and HUD-heavy situations, which is precisely where a lot of people notice frame drops.

SolarClient ships this stack pre-configured and version-matched, which is most of what the launcher is for — the combination is well established, but keeping it consistent across Minecraft versions by hand is tedious. There is a mod-by-mod breakdown in our guide to Minecraft performance mods.

Step 3: The settings that actually matter

Once the renderer is modern, settings have a different cost profile than the folklore suggests. These are the ones with real weight, in order:

Render distance

The most expensive setting in the game, and the one people leave highest. The number of loaded chunks grows with the square of the radius: a render distance of 16 loads roughly four times as many chunks as a render distance of 8, not twice as many. Every one of those chunks needs geometry built, stored in memory, and considered for drawing.

Twelve is a reasonable ceiling for most systems. Eight is comfortable on modest hardware and is still further than you can meaningfully see in most terrain. If you want long views specifically, Distant Horizons is a better answer than raising render distance — it renders far terrain as simplified level-of-detail geometry at a fraction of the cost.

Simulation distance

Separate from render distance since 1.18, and often overlooked. This controls how far away the world keeps simulating — mob AI, redstone, crop growth, block ticks. It affects TPS rather than FPS. If singleplayer feels laggy rather than choppy, lower this before touching anything visual. Most players notice nothing at 8.

Graphics mode

Fabulous is substantially more expensive than Fancy. It renders translucent surfaces into separate buffers so that water, glass, and particles composite correctly, which costs both VRAM and fill rate. Unless you specifically want correct translucency layering, Fancy looks nearly identical at a real discount. Fast is cheaper again and mainly changes leaves and water.

Biome blend

Smooths colour transitions between biomes by averaging colours over a radius. The cost is in chunk rebuilds, and it rises sharply with the setting. Vanilla’s default of 5×5 is defensible; anything higher is expensive for a subtle effect. Sodium handles this more efficiently than vanilla, but it is still not free.

Entity and particle settings

Entity distance and particle density matter most in exactly the places where FPS matters most: mob farms, busy servers, combat. Dropping particles to Decreased and entity distance to 75% or 50% costs little visually and helps precisely when you need it. EntityCulling goes further, skipping entities that are not actually visible from the camera.

VSync and frame rate cap

VSync locks output to your monitor’s refresh rate, which eliminates tearing at the cost of input latency and, when you cannot maintain the target, a disproportionate frame rate drop. Most players are better served by leaving VSync off and setting Max Framerate slightly below refresh rate — 141 on a 144 Hz panel, for example. That keeps latency low and the frame time steady.

One change at a time

Change a single setting, then watch the frame rate for thirty seconds in a consistent spot. Changing five settings together tells you nothing about which one helped, and people routinely keep four settings turned down for no benefit because they never isolated the one that mattered.

Step 4: Java version and memory

Two things here, and the second one is where most advice on the internet goes wrong.

Use the right Java version. Each Minecraft version targets a specific Java release, and running the wrong one produces anything from a silent performance penalty to a refusal to start. Newer Java releases also bring genuine runtime improvements. Our Java version guide has the full mapping; SolarClient handles this automatically.

Do not allocate more RAM than you need. This is counterintuitive enough that it needs stating plainly: giving Minecraft 16 GB when it needs 4 will usually make your stutter worse. A larger heap means more garbage accumulates between collections, and collecting more garbage takes longer. Vanilla with a performance mod stack is comfortable in 4 GB. Large modpacks want 6–8. Almost nothing benefits from more than that, and the downside is real. The RAM allocation guide covers the reasoning and the numbers in detail.

Garbage collector tuning is the other half of this. Well-chosen G1GC flags trade a slightly lower average throughput for much shorter individual pauses, which is exactly the right trade for a game — you would rather lose one frame consistently than drop twelve at once. Java 21 and later also offer generational ZGC, which targets sub-millisecond pauses and suits large modded heaps well.

Step 5: System-level fixes

Worth a pass once the game itself is in order:

  • Update your GPU drivers. Minecraft leans on OpenGL, which vendors historically treat as a second-class path. Driver updates have produced double-digit percentage changes in Minecraft specifically, in both directions — so note your version before updating.
  • Exclude your game directory from antivirus real-time scanning. Minecraft touches thousands of small files during chunk loading and world saving. On-access scanning of every one of them shows up as periodic hitching. Exclude the launcher and .minecraft directories, not your whole drive.
  • Close overlays. Discord, Steam, GeForce Experience, Xbox Game Bar, and RGB software all inject themselves into the rendering path. Discord’s overlay in particular has a long history of causing hitching in Java applications. Turn them off and test.
  • Set the Windows power plan to High performance on desktops, and make sure laptops are plugged in. Balanced plans downclock aggressively, and Minecraft’s bursty CPU pattern is exactly the kind that confuses a power governor.
  • Watch your RAM headroom. If the system is short on physical memory, Windows starts paging to disk, and a paged-out Java heap produces stutter that no in-game setting will fix. Leave at least 2–3 GB free for the OS.

How to measure whether any of it worked

Average FPS is a poor metric. A game that renders at a steady 60 feels far better than one that averages 90 while dropping to 20 four times a minute. What you care about is frame time consistency.

Practical approach:

  1. Pick a fixed spot — a specific location, facing a specific direction, at a specific time of day. Reuse it for every test.
  2. Open the F3 lag meter (Alt+F3 on most versions) and read the frame time graph rather than the average. Tall spikes are the thing to hunt; a flat line is the goal.
  3. Test for at least a minute. First-load chunk meshing distorts the first few seconds badly.
  4. Change one thing, retest, write it down.

If the graph shows regular spikes at roughly even intervals, that pattern is characteristic of garbage collection. Irregular spikes while moving point at chunk loading. A steady low number with no spikes means you are simply GPU- or CPU-bound and need to lower settings rather than fix a stall.

Things that don’t help (and why people think they do)

  • “Allocate 16 GB.” Covered above. It is the most widely repeated piece of bad Minecraft advice, and it survives because the person giving it also installed Sodium at the same time and credited the wrong change.
  • “Optimiser” and “booster” utilities. Programs that promise to speed up games by cleaning the registry or freeing RAM do nothing useful, and freeing RAM in particular is actively counterproductive — it forces the OS to discard caches it will immediately need again.
  • Setting Java to Realtime priority. Above-normal is defensible. Realtime can starve the kernel of scheduling time and make the whole system, including the game, worse.
  • Copying JVM flags from a ten-year-old forum post. Many widely circulated flag lists reference options that were removed from the JVM years ago, or enable collectors that no longer exist. On modern Java these are ignored at best and refuse to start at worst.
  • Turning down every setting at once. Once the renderer is modern, most low settings cost you visual quality for a rounding error in frame time. Find the two or three that matter on your hardware and leave the rest alone.

Where to go next

Work through the list in order and stop when the frame rate is where you want it. In practice most people find that the GPU selection fix and Sodium together account for nearly all of the improvement available to them, and everything after that is refinement.
